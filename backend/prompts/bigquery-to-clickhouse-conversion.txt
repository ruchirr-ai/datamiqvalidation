1. DATA TYPE MAPPING (BigQuery → ClickHouse)
   DIRECT MAPPINGS:
   - STRING          → String
   - INT64           → Int64
   - FLOAT64         → Float64
   - BOOL / BOOLEAN  → UInt8  (ClickHouse uses 0/1; or Bool alias in v22+)
   - NUMERIC(p,s)    → Decimal(p,s)
   - BIGNUMERIC(p,s) → Decimal(p,s)  — warn if precision exceeds Decimal128
   - DATE            → Date  (or Date32 if pre-1970 dates required)
   - DATETIME        → DateTime  (no timezone) or DateTime64(3) for milliseconds
   - TIMESTAMP       → DateTime64(6, 'UTC')  (BigQuery TIMESTAMP is always UTC)
   - TIME            → String  (ClickHouse has no native TIME type — store as String 'HH:MM:SS' or seconds since midnight as UInt32)
   - BYTES           → String  (store as hex or base64 encoded; warn user)
   - JSON            → String  (use JSON functions available in ClickHouse 22.6+)
   - GEOGRAPHY       → String  — NOT NATIVELY SUPPORTED; flag as High risk
   - INTERVAL        → No direct equivalent — must be converted to integer arithmetic

   COMPLEX TYPES:
   - ARRAY<T>        → Array(T)
   - STRUCT<f T,...> → Tuple(f T,...)  or named Tuple if ClickHouse version supports it
   - MAP<K,V>        → Map(K,V)  (ClickHouse 21.1+)
   - ARRAY<STRUCT>   → Array(Tuple(...))

   NULLABILITY:
   - ClickHouse columns are NOT NULL by default. Wrap with Nullable(T) only when nulls are truly expected.
   - Prefer non-Nullable types for performance (avoids extra null bitmap storage).

2. DDL / TABLE CREATION
   BigQuery syntax → ClickHouse syntax:
   - `CREATE TABLE project.dataset.table (...)` → `CREATE TABLE database.table (...) ENGINE = MergeTree()`
   - Always add `ENGINE = MergeTree()` (or appropriate variant: ReplacingMergeTree, AggregatingMergeTree, etc.)
   - Always add `ORDER BY` clause (required in MergeTree). Choose based on common filter/join columns or use `ORDER BY tuple()` as a fallback.
   - `PARTITION BY DATE_TRUNC('month', ts)` → `PARTITION BY toYYYYMM(ts)`
   - BigQuery CLUSTER BY col1,col2 → becomes the `ORDER BY (col1, col2)` in MergeTree
   - `OPTIONS(partition_expiration_days=N)` → `TTL date_col + INTERVAL N DAY` clause
   - BigQuery project.dataset.table three-part names → database.table (two-part only in ClickHouse)
   - `CREATE OR REPLACE TABLE` → `CREATE OR REPLACE TABLE` (supported in ClickHouse 22.5+)
   - `IF NOT EXISTS` → supported
   - `PRIMARY KEY` in BigQuery is non-enforced; in ClickHouse MergeTree ORDER BY serves as the physical sort key
   - Column OPTIONS like `DEFAULT` work similarly but BigQuery's `GENERATE_UUID()` → `generateUUIDv4()`

3. QUERY SYNTAX DIFFERENCES
   FROM / JOINs:
   - `FROM project.dataset.table` → `FROM database.table`
   - Backtick-quoted identifiers in BigQuery (``table``) → double-quoted or unquoted in ClickHouse
   - `CROSS JOIN UNNEST(arr) AS t` → `ARRAY JOIN arr AS t`  (preferred ClickHouse idiom)
   - `LEFT JOIN UNNEST(arr) AS t` → `LEFT ARRAY JOIN arr AS t`
   - `UNNEST(arr) WITH ORDINALITY` → `arrayEnumerate(arr)` for index; use `ARRAY JOIN` + `arrayEnumerate`
   - Comma-separated UNNEST (`FROM t, UNNEST(t.col) AS item`) → `ARRAY JOIN t.col AS item`

   SUBQUERIES / CTEs:
   - WITH (CTE) syntax is identical — supported in ClickHouse
   - Recursive CTEs: NOT SUPPORTED in ClickHouse — flag as High risk, suggest manual rewrite with `arrayMap` or iterative approach
   - Correlated subqueries: limited support in ClickHouse — flag any correlated subquery as Medium risk

   QUALIFY clause:
   - BigQuery `QUALIFY row_number() OVER (...) = 1` → wrap in outer SELECT with WHERE:
     `SELECT * FROM (SELECT *, row_number() OVER (...) AS rn FROM ...) WHERE rn = 1`

   - `FORMAT_DATE('%Y-%m-%d', d)`      → `formatDateTime(d, '%Y-%m-%d')`

   - `PARSE_DATE('%Y-%m-%d', str)`     → `toDate(str)` (if ISO) or `parseDateTime(str, '%Y-%m-%d')`

   - `ARRAY_AGG(x ORDER BY y)`         → `groupArraySorted(x)` or `arraySort(groupArray(x))`
   - `ARRAY_AGG(x LIMIT n)`            → `groupArraySample(n)(x)` or `groupArray(n)(x)`
   - `ANY_VALUE(x)`                    → `any(x)`
   - `APPROX_COUNT_DISTINCT(x)`        → `uniq(x)` (HyperLogLog-based, like BQ)
   - `APPROX_QUANTILES(x, n)`          → `quantilesExact(0.1,...)(x)` — manual percentile specification needed
   - `APPROX_TOP_COUNT(x, n)`          → `topK(n)(x)`
   - `BIT_AND(x)` / `BIT_OR(x)` / `BIT_XOR(x)` → `groupBitAnd(x)` / `groupBitOr(x)` / `groupBitXor(x)`

   - `ARRAY_REVERSE(arr)`              → `arrayReverse(arr)`
   - `ARRAY_TO_STRING(arr, delim)`     → `arrayStringConcat(arr, delim)`

   - `LAG(x, n, default)` / `LEAD` → supported
   - `CUME_DIST()` / `PERCENT_RANK()` → supported
   - `RATIO_TO_REPORT(x) OVER (...)` → NOT SUPPORTED — rewrite as `x / SUM(x) OVER (...)`
   - BigQuery RANGE BETWEEN with INTERVAL → NOT SUPPORTED in CH — flag as High risk

5. DML / MUTATION LIMITATIONS
   - `INSERT INTO ... VALUES` → supported
   - `INSERT INTO ... SELECT` → supported
   - `UPDATE table SET ... WHERE ...` → requires `ALTER TABLE ... UPDATE` syntax in ClickHouse (asynchronous mutation)
     Convert: `UPDATE t SET col=val WHERE cond` → `ALTER TABLE t UPDATE col=val WHERE cond`
     WARN: CH mutations are asynchronous and not transactional
   - `DELETE FROM table WHERE ...` → `ALTER TABLE t DELETE WHERE cond` (async mutation)
     Convert: `DELETE FROM t WHERE cond` → `ALTER TABLE t DELETE WHERE cond`
     WARN: CH deletes are asynchronous; for lightweight deletes use `DELETE FROM t WHERE cond` in CH 23.3+ (ReplacingMergeTree or lightweight delete mode)
   - `MERGE INTO target USING source ON (...) WHEN MATCHED THEN UPDATE ... WHEN NOT MATCHED THEN INSERT` →
     NOT NATIVELY SUPPORTED as a single atomic statement — flag as High risk
     Rewrite: perform separate INSERT and ALTER TABLE UPDATE; or use ReplacingMergeTree with deduplication
   - BigQuery scripting (DECLARE, SET, CALL, LOOP, WHILE, IF...END IF, EXCEPTION/BEGIN) →
     NOT SUPPORTED as standard SQL in ClickHouse — ClickHouse has no server-side procedural language
     These must be rewritten as application-layer logic or materialized views

6. VIEWS
   - `CREATE VIEW db.view_name AS SELECT ...` → identical syntax, supported
   - `CREATE MATERIALIZED VIEW db.view_name TO db.target_table AS SELECT ...` → supported
   - BigQuery scheduled queries → ClickHouse materialized views with Kafka/file/S3 engines, or external schedulers
   - `CREATE OR REPLACE VIEW` → supported in ClickHouse 22.5+

7. STORED PROCEDURES / FUNCTIONS
   - BigQuery scripting-based stored procedures (CREATE PROCEDURE) → NOT SUPPORTED in ClickHouse
     Convert to: ClickHouse UDFs (User Defined Functions) for pure expressions, or application-layer code
   - `CREATE FUNCTION name(params) AS (expr)` (scalar) → `CREATE FUNCTION name AS (params) -> expr` in ClickHouse
   - `CREATE TABLE FUNCTION` → supported via table-valued functions in CH
   - JavaScript UDFs (BigQuery) → NOT SUPPORTED — must rewrite in Python/C++ external UDF or SQL lambda
   - Temporary functions (CREATE TEMP FUNCTION) → no direct equivalent; inline expression or WITH alias

8. IDENTIFIERS AND QUOTING
   - BigQuery uses backticks for reserved word quoting: ``column_name`` → use double quotes "column_name" or no quotes if safe
   - BigQuery project.dataset.table → ClickHouse database.table (remove project name)
   - ClickHouse is case-sensitive for database and table names; function names are case-insensitive
   - Avoid using BigQuery-specific reserved words as identifiers

9. PARTITIONING & ENGINE SELECTION GUIDE
   Choose the correct ClickHouse table engine:
   - Standard append-only analytics tables → `MergeTree()`
   - Need deduplication / updates by primary key → `ReplacingMergeTree([version_col])`
   - Need sum/max aggregations pre-aggregated → `AggregatingMergeTree()`
   - Need FIFO TTL deletion → `MergeTree()` with TTL clause
   - Replicated production tables → `ReplicatedMergeTree('/zookeeper/path', 'replica_name')`
   - Always specify `ORDER BY` (required). For unkeyed tables use `ORDER BY tuple()`

10. KNOWN FEATURE GAPS (High Risk — Flag Always)
    The following BigQuery features have NO direct equivalent in ClickHouse and require manual intervention:
    - INFORMATION_SCHEMA queries (mostly different schema; some overlap)
    - Row-level security / Column-level security policies → manage at application layer
    - Authorized views / authorized datasets → no concept in CH; use table-level permissions
    - BigQuery ML (BQML) models (CREATE MODEL, ML.PREDICT) → NOT SUPPORTED
    - EXTERNAL TABLE over Google Drive / Sheets → no equivalent
    - BigQuery scripting (DECLARE, SET, EXCEPTION blocks) → no server-side scripting
    - PIVOT / UNPIVOT keywords → NOT SUPPORTED natively — rewrite with conditional aggregation
      `PIVOT: SUM(CASE WHEN col='val' THEN metric END)` pattern
    - SELECT * EXCEPT → NOT SUPPORTED — list columns explicitly
    - SELECT * REPLACE → NOT SUPPORTED — list columns with expressions
    - WITH RECURSIVE (recursive CTEs) → NOT SUPPORTED
    - Time travel queries (FOR SYSTEM_TIME AS OF) → NOT SUPPORTED
    - EXPORT DATA statement → use INSERT INTO ... SELECT with S3/file engines
    - Wildcard table names (`FROM dataset.events_*`) → NOT SUPPORTED — use UNION ALL or merge engine
    - TABLESAMPLE → NOT SUPPORTED — use `LIMIT ... BY` or `WHERE rand() < ratio`
    - ASSERT statements → remove
    - CREATE SCHEMA / DROP SCHEMA → use CREATE DATABASE / DROP DATABASE
